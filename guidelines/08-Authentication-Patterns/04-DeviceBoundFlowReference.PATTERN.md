# Device-Bound Refresh Token — Generic Auth Flow Reference

A sign-up/login/auto-login design combining OTP email verification,
password login, and a rotating refresh mechanism cryptographically bound
to a specific browser via a non-extractable WebCrypto key pair — so a
stolen refresh token alone is useless without also possessing the
private key, which never leaves the browser. Assumes a project already
has its own `User` model (with a hashed password field) and an OTP/
verification-code model — referenced generically below, not repeated
here, since their exact shape is project-specific.

**Status:** Flows 1 through 5 (Sign Up, Log In, Auto-login, Password
Reset Session Invalidation, Logout) are all worked through in full
below. This is v2 of the design — incorporates fixes for four issues
found during review of the original version: a cross-tab race condition
in Flow 3, a fragile fingerprint computation, missing session
invalidation on password reset, and a missing logout flow.

---

## Why This Pattern, Instead of an httpOnly Refresh Cookie

**One root cause, one symptom — not two separate reasons.** The
motivation for this design is cross-site cookie restrictions in modern
browsers, specifically **Safari's Intelligent Tracking Prevention (ITP)
and Firefox's Enhanced Tracking Protection (ETP)**, both of which block
third-party/cross-site cookies by default, unconditionally, as standing
platform policy — not a configurable heuristic, not something a cookie
attribute can work around. **Chrome is the exception, not the rule
here** — it abandoned its own plan to fully deprecate third-party
cookies in 2024, and currently does not block them by default in normal
browsing (only in Incognito, plus an explicit user choice some people
make). So this isn't accurately described as "all modern browsers block
this" — it's specifically Safari and Firefox, which is still more than
enough real traffic to make it a genuine, current problem.

**"Auto-login breaking" is the visible symptom of this, not an
independent second reason for the switch.** If the browser silently
drops, restricts, or aggressively expires a cross-site cookie (exactly
what ITP/ETP do), the thing a user actually experiences is auto-login
failing unpredictably — even though nothing in the application logic
itself is wrong. Framing "solves auto-login" and "avoids cross-site
cookie blocking" as two separate, co-equal motivations is imprecise;
there is one cause, and this is its symptom.

**Adopted as this scaffold's general default, not a workaround for one
specific deployment topology.** A reusable scaffold has to work
correctly regardless of how a given project ends up hosted — same
domain, same site via subdomains, or genuinely separate domains — and
in practice, all three happen across real projects. An httpOnly-cookie
approach would force a per-project decision (safe on shared-site
deployments, broken on cross-site ones), meaning the scaffold would need
two different auth implementations, or someone would have to remember
to switch depending on hosting. This design sidesteps that entirely: it
never relies on the browser automatically attaching anything
cross-origin (the access token is manually attached via header, the
device token manually read from `localStorage` and sent in the request
body), so it works identically correctly no matter which topology a
given project ends up using. See the companion reference,
[httpOnly Cookie + JWT](05-HttpOnlyCookieFlowReference.PATTERN.md), for the httpOnly-cookie pattern this
one is compared against, including exactly when that pattern *is* the
right, simpler choice — same-origin/same-site deployments, where this
extra complexity isn't needed at all.

## Terminology (to avoid the confusion earlier drafts ran into)

- **Access token** — short-lived (15 min), kept in frontend memory only,
  sent as a normal `Authorization` header on every API request. Never
  persisted anywhere.
- **Device token** — a random value generated by the backend, sent to
  the browser once, stored in `localStorage`. Its only job is acting as
  a lookup key — "which RefreshRecord does this browser belong to." It
  is not itself a credential with authority; the server always goes and
  checks the real record before trusting anything.
- **RefreshRecord** — lives only in the database, never sent anywhere.
  The actual source of truth for whether a device's session is still
  valid. One record per device/browser, not one per user — the same
  person can be logged in on multiple devices simultaneously, each with
  its own record (same reasoning as `PushSubscription` in the main
  spec).
- **Browser key pair** — generated client-side via
  `crypto.subtle.generateKey(..., false, ...)`. The private half is
  non-extractable — not even the page's own JavaScript can ever read
  its raw value, only ask the browser to sign things with it. Reused
  across sessions on the same device (persisted as a `CryptoKey` object
  in IndexedDB, not localStorage, since localStorage can only hold
  strings).
- **publicKeyFingerprint** — a canonical SHA-256 thumbprint of the
  exported public key (RFC 7638 — see below), stored alongside it on
  `RefreshRecord`. Exists purely so the database can index and query
  "does this account already have a record for this device" quickly —
  querying against the raw public key object directly isn't practical.
  **v2 change:** v1 used a plain `JSON.stringify` of the JWK, which is
  fragile — JWK field export order isn't guaranteed stable across
  browser versions, so the same logical key could re-export with a
  different field order and silently produce a different fingerprint.
  RFC 7638 defines a fixed, canonical member set/order specifically to
  prevent this.
- **Web Locks API** (`navigator.locks`) — a browser API for coordinating
  work across multiple tabs/workers of the same origin. Used in Flow 3
  (v2) to serialize refresh attempts across tabs, so two tabs never
  race to consume the same device token.

## Flow 1: Sign Up — full detail

**What happens, in order:**
1. Name, email, password submitted → account created (unverified),
   password hashed, 6-digit OTP emailed.
2. Person enters the OTP. Right before submitting, the browser generates
   its key pair and exports the public half.
3. One request goes out: OTP code + exported public key, together.
4. Backend checks the OTP (correct, not expired, not already used),
   marks the account verified, stores the public key and its canonical
   fingerprint, generates a device token (sent once) and its hash
   (stored), creates the RefreshRecord, and returns both the access
   token and device token.
5. Frontend keeps the access token in memory, saves the device token to
   `localStorage`.

### Frontend

```js
const otpCode = "482913"; // from the input field

const keyPair = await crypto.subtle.generateKey(
  { name: "ECDSA", namedCurve: "P-256" },
  false,
  ["sign", "verify"]
);

const publicKeyExported = await crypto.subtle.exportKey("jwk", keyPair.publicKey);

const { data } = await axios.post("/api/auth/verify-otp", {
  otp: otpCode,
  publicKey: publicKeyExported
});

// data.accessToken → keep in app state (memory)
// data.deviceToken → persist for auto-login
localStorage.setItem("deviceToken", data.deviceToken);
```

### Backend

```js
const { webcrypto, randomBytes, createHash } = require("crypto");
const bcrypt = require("bcrypt");
const jwt = require("jsonwebtoken");
const { addDays } = require("date-fns");

// v2: RFC 7638 canonical JWK thumbprint — replaces v1's plain
// JSON.stringify(publicKey), which was order-dependent and could
// silently fingerprint the same logical key two different ways.
// Shared by Flow 1 and Flow 2's backend code.
function canonicalizeJwk(jwk) {
  return JSON.stringify({
    crv: jwk.crv,
    kty: jwk.kty,
    x: jwk.x,
    y: jwk.y
  });
}

app.post("/api/auth/verify-otp", async (req, res) => {
  const { otp, publicKey } = req.body;

  const otpRecord = await OtpCode.findOne({
    user: req.pendingUserId,
    purpose: "signup_verification",
    consumedAt: null
  });

  if (!otpRecord) {
    return res.status(400).json({ error: "Invalid or expired code" });
  }

  const isCorrectCode = await bcrypt.compare(otp, otpRecord.codeHash);
  const isExpired = otpRecord.expiresAt < new Date();

  if (!isCorrectCode || isExpired) {
    return res.status(400).json({ error: "Invalid or expired code" });
  }

  otpRecord.consumedAt = new Date();
  await otpRecord.save();

  const user = await User.findByIdAndUpdate(
    otpRecord.user,
    { emailVerified: true },
    { new: true }
  );

  // Confirms the key is well-formed and usable — the actual signature
  // check happens later, in Flow 3
  await webcrypto.subtle.importKey(
    "jwk",
    publicKey,
    { name: "ECDSA", namedCurve: "P-256" },
    true,
    ["verify"]
  );

  const publicKeyFingerprint = createHash("sha256")
    .update(canonicalizeJwk(publicKey))
    .digest("hex");

  const deviceToken = randomBytes(32).toString("hex");
  const deviceTokenHash = createHash("sha256").update(deviceToken).digest("hex");

  await RefreshRecord.create({
    user: user._id,
    publicKeyJwk: publicKey,
    publicKeyFingerprint,
    deviceTokenHash,
    used: false,
    expiresAt: addDays(new Date(), 60)
  });

  const accessToken = jwt.sign({ userId: user._id }, process.env.JWT_SECRET, {
    expiresIn: "15m"
  });

  res.json({ accessToken, deviceToken });
});
```

## Flow 2: Log In — full detail

**What happens, in order:**
1. Person enters email and password.
2. Browser checks IndexedDB for an existing key pair on this device. If
   one exists, reuse it. If not, generate a new one (same as Flow 1).
3. One request goes out: email + password + exported public key,
   together.
4. Backend checks the password first — **this alone confirms identity**,
   no key/proof involved in that check. Only after the password is
   confirmed does the backend touch the key, purely to safely issue
   this device a device token.
5. Backend looks up whether a RefreshRecord already exists for this
   exact user + device (matched by `publicKeyFingerprint`) and either
   updates it in place or creates a new one — a single `upsert` query,
   not a separate find-then-decide step.
6. Returns a fresh access token + device token, same shape as Flow 1.

### Frontend

```js
const email = "jordan@studio.com";
const password = "••••••••";

let keyPair = await getStoredKeyPair(); // retrieves a previously-saved,
                                         // non-extractable CryptoKey from
                                         // IndexedDB, if this device has
                                         // logged in before
if (!keyPair) {
  keyPair = await crypto.subtle.generateKey(
    { name: "ECDSA", namedCurve: "P-256" },
    false,
    ["sign", "verify"]
  );
  await storeKeyPair(keyPair); // save it in IndexedDB for next time
}

const publicKeyExported = await crypto.subtle.exportKey("jwk", keyPair.publicKey);

const { data } = await axios.post("/api/auth/login", {
  email,
  password,
  publicKey: publicKeyExported
});

localStorage.setItem("deviceToken", data.deviceToken);
```

### Backend

Uses the same imports as Flow 1's backend code (`webcrypto`,
`randomBytes`, `createHash`, `bcrypt`, `jwt`, `addDays`,
`canonicalizeJwk`).

```js
app.post("/api/auth/login", async (req, res) => {
  const { email, password, publicKey } = req.body;

  const user = await User.findOne({ email });

  if (!user) {
    return res.status(401).json({ error: "Invalid email or password" });
  }

  const isCorrectPassword = await bcrypt.compare(password, user.passwordHash);

  if (!isCorrectPassword) {
    return res.status(401).json({ error: "Invalid email or password" });
  }

  // Identity is already confirmed above. Everything from here is just
  // safely issuing this device a device token — not part of the login
  // check itself.
  await webcrypto.subtle.importKey(
    "jwk",
    publicKey,
    { name: "ECDSA", namedCurve: "P-256" },
    true,
    ["verify"]
  );

  const publicKeyFingerprint = createHash("sha256")
    .update(canonicalizeJwk(publicKey))
    .digest("hex");

  const deviceToken = randomBytes(32).toString("hex");
  const deviceTokenHash = createHash("sha256").update(deviceToken).digest("hex");

  // One record per (user, device) pair. A returning device updates its
  // own existing record in place; a new device creates one.
  await RefreshRecord.findOneAndUpdate(
    { user: user._id, publicKeyFingerprint },
    {
      user: user._id,
      publicKeyJwk: publicKey,
      publicKeyFingerprint,
      deviceTokenHash,
      used: false,
      expiresAt: addDays(new Date(), 60)
    },
    { upsert: true }
  );

  const accessToken = jwt.sign({ userId: user._id }, process.env.JWT_SECRET, {
    expiresIn: "15m"
  });

  res.json({ accessToken, deviceToken });
});
```

## Data model: RefreshRecord

Not yet part of a project's main technical spec — add it there once this
design is finalized. Used identically by Flows 1, 2, 3, and 5.

```
RefreshRecord
  user                  ObjectId → User
  publicKeyJwk          Object — the raw JWK, re-imported whenever a
                        signature needs checking (Flow 3)
  publicKeyFingerprint  String — RFC 7638 canonical SHA-256 thumbprint
                        of publicKeyJwk (v2 — was a plain
                        JSON.stringify hash in v1), indexed, used to
                        find "this user's record for this device"
                        quickly and reliably regardless of how a given
                        browser orders JWK export fields
  deviceTokenHash       String — SHA-256 hash (not bcrypt — the token
                        is already high-entropy and random, unlike a
                        password, and this field needs to be directly
                        queryable, which a bcrypt hash can't be). Raw
                        device token is never stored, only sent to the
                        browser once.
  used                  Boolean, default false — flips true on first
                        use, enabling reuse detection
  usedAt                Date, default null — v2 addition. Set alongside
                        `used = true`. Powers Flow 3's grace-window
                        check (below) — distinguishing a benign
                        same-device race from genuine token theft
                        requires knowing not just THAT a token was
                        reused, but WHEN the original use happened.
  expiresAt             Date — hard cutoff regardless of use
```

**Index required:**
```js
refreshRecordSchema.index({ user: 1, publicKeyFingerprint: 1 });
```
Makes the Flow 2 upsert query and any future per-device lookup fast
regardless of collection size — the same kind of index already used for
`user`-scoped queries elsewhere in the spec (`Category`, `Message`).

**Optional, not yet decided either way:** a TTL index on `expiresAt`
(`{ expires: 0 }`) would let MongoDB automatically delete expired
records with no cleanup job needed. Not required by anything above —
worth considering separately.

**Design decisions made along the way, worth remembering:**
- The device token is independently random, *not* derived from the
  public key — deriving it from the key would make it computable by
  anyone who ever saw the public key on the wire, since public keys
  aren't secret by design.
- Identity verification (OTP in Flow 1, password in Flow 2) and
  device-token setup (the key/public-key step) happen in **one combined
  request**, not two round trips.
- Login does not require a signed proof as part of confirming identity
  — the password check alone does that. The key only comes into play
  afterward, to safely issue the device a token.
- One `RefreshRecord` per (user, device) pair, found via
  `publicKeyFingerprint` — not one per user (would overwrite other
  devices) and not a new record on every login (would pile up
  unbounded). This mirrors why `PushSubscription` is its own collection
  in the main spec rather than fields on `User`.
- **v2:** the fingerprint is computed via RFC 7638's canonical
  thumbprint, not a plain `JSON.stringify` — see Terminology above.

## Flow 3: Auto-login — full detail

**What happens, in order:**
1. App loads with nothing in memory (no access token — it never
   survives a closed tab).
2. Frontend checks `localStorage` for a saved device token. None found
   → normal login screen. Found → continue.
3. **v2:** the refresh attempt is wrapped in a Web Locks request, so
   only one tab of this browser ever attempts a refresh at a time —
   see "Why Flow 3 needed a cross-tab fix" below.
4. Frontend retrieves this device's key from IndexedDB and signs the
   *current* device token (re-read from `localStorage` after the lock
   is acquired, not the value read in step 2) with it (no timestamp
   involved — see note below).
5. One request goes out: the device token, plus the signature.
6. Backend hashes the incoming device token, looks up the matching
   RefreshRecord, and checks, in order: does it exist and is it
   unexpired; has it already been used before (and if so, is this
   within the grace window — v2, see below); does the signature verify
   against the record's stored public key.
7. All pass → mark that record `used` (with `usedAt`), create a fresh
   one (same upsert-by-device shape as Flow 2), return a new access
   token + new device token.
8. Device token matches a record already marked `used`, and it's
   **outside** the grace window → treat as theft: every RefreshRecord
   for that user gets deleted, forcing a real login again, on every
   device.

**No timestamp/freshness window on the signature itself is used** (this
is separate from the v2 grace-window addition below, which is about
`usedAt`, not the signature). An earlier draft of this flow included a
signature timestamp, but it turned out to add no real protection beyond
what reuse detection already provides — any replayed request gets
caught by `used` regardless of how old it is — while adding real risk
of rejecting a legitimate browser for no security benefit. Dropped.

**Verification only ever needs the public key, never the private one.**
Signing and verifying are different operations using different halves
of the key pair — the server reconstructs the plain data that was
signed (just the device token) and checks the arriving signature
against it using the public key already stored from Flow 1/2. The
private key is never involved on the server side, at any point.

### Why Flow 3 needed a cross-tab fix (v2)

**The problem (v1):** `localStorage` is shared across every tab of the
same origin. If two tabs of the same browser both have their access
token expire around the same time (plausible — same 15-minute window,
tabs opened together) and both independently attempt Flow 3, they race:
whichever request the server processes first rotates the device token;
the second tab's request then presents a token already marked `used` —
which, in v1, triggered the full theft response, logging the user out
of *every* device for doing nothing wrong.

**The fix — two layers, not one:**

**1. Frontend: Web Locks API**, coordinating tabs of the same origin so
only one ever attempts a refresh at a time:

```js
const deviceToken = localStorage.getItem("deviceToken");

if (!deviceToken) {
  // no saved session on this device — show the normal login screen
} else {
  const { accessToken } = await navigator.locks.request("auth-refresh", async () => {
    // Re-read now that the lock is held — another tab may have
    // already rotated this while this tab was waiting for the lock.
    // Always use whatever is CURRENTLY in localStorage at this point,
    // never the value read before the lock was requested.
    const currentDeviceToken = localStorage.getItem("deviceToken");

    const keyPair = await getStoredKeyPair(); // from IndexedDB — the
                                               // same key used regardless
                                               // of which tab is refreshing,
                                               // since it's one key per device

    const encodedPayload = new TextEncoder().encode(
      JSON.stringify({ deviceToken: currentDeviceToken })
    );

    const signatureBuffer = await crypto.subtle.sign(
      { name: "ECDSA", hash: "SHA-256" },
      keyPair.privateKey,
      encodedPayload
    );

    const signature = btoa(String.fromCharCode(...new Uint8Array(signatureBuffer)));

    const { data } = await axios.post("/api/auth/refresh", {
      deviceToken: currentDeviceToken,
      signature
    });

    localStorage.setItem("deviceToken", data.deviceToken); // old one is
                                                             // now dead
    return { accessToken: data.accessToken };
  });

  // accessToken → keep in this tab's own memory
}
```
Each tab still makes its own call (each tab needs its own access token
in its own memory — access tokens are never shared via `localStorage`),
but calls are now serialized, and each one always uses the freshest
token available at the moment it actually runs — never a stale one
captured before waiting began. In the common case, this alone prevents
the race entirely.

**2. Backend: a short grace window, as a safety net for what the lock
can't guarantee** — browsers without Web Locks support (older Safari),
or any other path that bypasses the lock. If a device token is reused
very shortly after its own rotation, treat it as a likely benign
same-device race rather than theft — verify and rotate again normally,
rather than locking out every device:

```js
const GRACE_WINDOW_MS = 10_000; // 10 seconds

if (record.used) {
  const withinGraceWindow =
    record.usedAt && (Date.now() - record.usedAt.getTime()) < GRACE_WINDOW_MS;

  if (!withinGraceWindow) {
    // Outside the grace window — reused this long after rotation is
    // treated as theft, exactly as in v1.
    await RefreshRecord.deleteMany({ user: record.user });
    return res.status(401).json({ error: "Session revoked, please log in again" });
  }
  // Within the grace window — fall through and treat this as an
  // ordinary valid refresh (verify + rotate again below), instead of
  // an attack.
}
```

**The honest tradeoff, stated plainly, not hidden:** the grace window
narrows the theft-detection window rather than eliminating it — an
attacker racing a legitimate refresh within the same ~10 seconds could
slip through undetected. This is the same tradeoff established
refresh-token-rotation systems elsewhere make deliberately (a bounded
grace period, not unbounded tolerance) — accepted here for the same
reason: eliminating false-positive lockouts from ordinary multi-tab use
is worth a narrow, bounded window, while anything outside that window is
caught exactly as before.

### Frontend (full Flow 3, with the Web Locks wrapper above)

See "Why Flow 3 needed a cross-tab fix" above for the complete frontend
code — it replaces what would otherwise be a bare (unwrapped) version of
the same request.

### Backend

```js
app.post("/api/auth/refresh", async (req, res) => {
  const { deviceToken, signature } = req.body;

  const deviceTokenHash = createHash("sha256").update(deviceToken).digest("hex");
  const record = await RefreshRecord.findOne({ deviceTokenHash });

  if (!record || record.expiresAt < new Date()) {
    return res.status(401).json({ error: "Invalid session" });
  }

  const GRACE_WINDOW_MS = 10_000;

  if (record.used) {
    const withinGraceWindow =
      record.usedAt && (Date.now() - record.usedAt.getTime()) < GRACE_WINDOW_MS;

    if (!withinGraceWindow) {
      // Already consumed once, and not within the benign-race grace
      // window — a second presentation means a copy exists somewhere
      // it shouldn't. Full compromise response: kill every record for
      // this user, across every device.
      await RefreshRecord.deleteMany({ user: record.user });
      return res.status(401).json({ error: "Session revoked, please log in again" });
    }
    // Within the grace window — treated as an ordinary refresh below,
    // not an attack.
  }

  const importedPublicKey = await webcrypto.subtle.importKey(
    "jwk",
    record.publicKeyJwk,
    { name: "ECDSA", namedCurve: "P-256" },
    true,
    ["verify"]
  );

  const isValidSignature = await webcrypto.subtle.verify(
    { name: "ECDSA", hash: "SHA-256" },
    importedPublicKey,
    Buffer.from(signature, "base64"),
    new TextEncoder().encode(JSON.stringify({ deviceToken }))
  );

  if (!isValidSignature) {
    return res.status(401).json({ error: "Invalid session" });
  }

  record.used = true;
  record.usedAt = new Date();
  await record.save();

  const newDeviceToken = randomBytes(32).toString("hex");

  await RefreshRecord.create({
    user: record.user,
    publicKeyJwk: record.publicKeyJwk,
    publicKeyFingerprint: record.publicKeyFingerprint,
    deviceTokenHash: createHash("sha256").update(newDeviceToken).digest("hex"),
    used: false,
    expiresAt: addDays(new Date(), 60)
  });

  const accessToken = jwt.sign({ userId: record.user }, process.env.JWT_SECRET, {
    expiresIn: "15m"
  });

  res.json({ accessToken, deviceToken: newDeviceToken });
});
```

**A known, accepted gap, not fixed:** the check-then-claim of a device
token (read `used`, then write `used: true`) happens as two separate
steps, not one atomic database operation. A genuinely simultaneous
double-request for the same token has a narrow window where both could
slip through. A fix exists (an atomic `findOneAndUpdate` claiming
`used: false` in one step) but was deliberately left out — the scenario
is rare, and the fix doesn't address the broader live-code-on-the-page
risk described below anyway, so it wasn't worth the added complexity for
this stage. (Note: this is a *different* gap from the cross-tab race
fixed above — this one is about two truly simultaneous requests for the
*same* token slipping past the read-then-write check itself, not about
one tab presenting an already-rotated token.)

### What each check in Flow 3 is actually for

| Check | Question it answers | Catches |
|---|---|---|
| `record.expiresAt` | Is this device's session still within 60 days? | Long-dead, abandoned sessions |
| `record.used` (+ `usedAt` grace window, v2) | Has this device token been consumed before, and if so, was it long enough ago to treat as theft rather than a benign same-device race? | A stolen *copy* of the token being reused, regardless of when — while tolerating ordinary multi-tab timing |
| `isValidSignature` | Was this signed by the original browser's key? | A stolen copy used from anywhere else — the one check a copy alone can't fake |

### What this flow does and doesn't defend against

Two different things can happen once malicious code is running on a
page at all (getting it running there in the first place is a separate
problem — cross-site scripting, XSS — not something this auth design
addresses):

- **A copy is stolen and used later, elsewhere.** Rotation and the
  signature requirement together fully close this — a stolen device
  token alone is useless without the private key, which can never be
  extracted or copied, and even a full theft only ever earns one
  attempted use before it's caught and the whole account is locked
  down (outside the v2 grace window — see the honest tradeoff noted
  above).
- **Malicious code stays live on the page and rides along in real
  time**, using whatever the page can currently do at that moment,
  without ever needing to steal or present anything. No auth design —
  this one, an httpOnly cookie, anything client-reachable — can close
  this, because it doesn't depend on stealing the right value at all.
  The real defense is stopping malicious code from running on the page
  in the first place (safe rendering of any external content, a strict
  Content-Security-Policy) — general web security practice, unrelated
  to how sign up, log in, or auto-login work. Worth tracking as a
  separate, ongoing concern outside this document's scope.

## Flow 4: Password Reset — Session Invalidation (v2, new)

**Not a full auth flow of its own** — the actual password reset
mechanism (requesting it, verifying it, the OTP/token used to authorize
setting a new password) lives in the main spec and isn't repeated here,
same referencing approach as the models noted at the top of this
document. This section covers only the one thing that was missing: what
happens to existing sessions when a password reset completes.

**The gap this closes:** without this, a device session issued *before*
a password compromise stays fully valid even *after* the compromised
password itself is fixed — the whole point of resetting a compromised
password is undermined if whatever already-open sessions exist keep
working regardless.

**The fix — one line, added wherever the password reset flow already
sets the new `passwordHash` on `User`:**

```js
// Wherever the existing password-reset flow finishes hashing and
// saving the new password:
await RefreshRecord.deleteMany({ user: user._id });
```

Same call already used for the Flow 3 theft-response case, triggered by
a different event. Forces a real login, on every device, the next time
each one needs to refresh — exactly the same experience a user already
gets after the theft-response path in Flow 3, applied here to a
different trigger.

## Flow 5: Logout (v2, new)

**What happens, in order:**
1. User clicks "log out."
2. Frontend sends the device token (already known, from `localStorage`)
   to the backend, on an authenticated request.
3. Backend deletes **only this device's** RefreshRecord — not every
   device's, unlike the Flow 3 theft-response path.
4. Frontend clears the device token from `localStorage`.
5. Frontend does **not** clear the IndexedDB key pair — deliberately.
   Flow 2 already reuses an existing key pair on the same device if one
   exists; keeping it means logging back in on the same device later
   skips key generation entirely, consistent with that existing logic.
   The key pair is device-scoped, not session-scoped — logging out of
   the account doesn't and shouldn't change which device this is.

### Frontend

```js
const deviceToken = localStorage.getItem("deviceToken");

await axios.post(
  "/api/auth/logout",
  { deviceToken },
  { headers: { Authorization: `Bearer ${accessToken}` } } // accessToken
                                                            // from wherever
                                                            // this app keeps
                                                            // it in memory
);

localStorage.removeItem("deviceToken");
// IndexedDB key pair intentionally left alone — see note above
```

### Backend

```js
app.post("/api/auth/logout", requireAuth, async (req, res) => {
  const { deviceToken } = req.body;

  const deviceTokenHash = createHash("sha256").update(deviceToken).digest("hex");

  // Scoped to req.user._id (from requireAuth) as well as the token
  // hash — a device token has enough entropy that guessing one is
  // infeasible regardless, but requiring both keeps this consistent
  // with how every other authenticated action already works, and
  // guarantees a caller can only ever log out their own device.
  await RefreshRecord.deleteOne({
    user: req.user._id,
    deviceTokenHash
  });

  res.json({ success: true });
});
```
`requireAuth` — the existing access-token-checking middleware already
used elsewhere in the API, not something new introduced here.
